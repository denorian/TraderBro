## 3. Неисправленные дефекты (перенос из прошлого ревью)

### 3.1. A7 — формула риска `FuturesPositionSizer` занижает риск на контракт

**Файл:** `src/main/java/com/traderbro/core/strategies/FuturesPositionSizer.java:60-66`

Текущий код:

```java
BigDecimal stopDistPts = entryPrice.subtract(stopPrice).abs()
        .divide(spec.getMinPriceIncrement(), 8, RoundingMode.HALF_UP);   // ← это ТИКИ, не пункты
BigDecimal riskPerContract = stopDistPts.multiply(spec.pointValue());
```

`FutureSpec.pointValue()` (`FutureSpec.java:36-41`) = `minPriceIncrementAmount / minPriceIncrement`,
т.е. **рубли за один пункт цены**. Стоп-дистанция `|entry − stop|` уже в пунктах цены. Деля её
ещё раз на `minPriceIncrement`, код получает тики и умножает их на рубли-за-пункт. При тике > 1
(напр. RTS: тик = 10 пунктов) риск на контракт занижается в `minPriceIncrement` раз → сайзер
выдаёт во столько же раз **больше** контрактов, чем позволяет риск-капитал.

**Рекомендация по исправлению:**

```java
BigDecimal stopDistance = entryPrice.subtract(stopPrice).abs();          // пункты цены
BigDecimal riskPerContract = stopDistance.multiply(spec.pointValue());   // руб/контракт
```

Тест `FuturesPositionSizerTest` маскирует дефект: во всех фикстурах `minPriceIncrement = 1`
(`FuturesPositionSizerTest.java:20`), при котором деление — no-op. Добавить кейс с реалистичной
спецификацией (напр. `minPriceIncrement=10`, `minPriceIncrementAmount=13` → pointValue=1.3 ₽/п.,
стоп-дистанция 100 п. → риск/контракт = 130 ₽, а не 13 ₽) и проверить число контрактов.

**Смягчающее обстоятельство:** класс — мёртвый код (см. A8), до продакшен-пути не доходит.
Исправлять обязательно **до** подключения, не после.

### 3.2. A8 — фьючерсы в боевом контуре сайзятся акционным `PositionSizer`

**Файлы:** `src/main/java/com/traderbro/scheduler/SignalEngine.java:164-167`,
`src/main/java/com/traderbro/execution/order/OrderManager.java:200-205`

`SignalEngine.submitOrder` для любого инструмента вызывает акционный `PositionSizer`
(`PositionSizer.java:37-57`): бюджет = `maxPositionPct × портфель`, лоты = бюджет/(цена×лот).
Для фьючерса это игнорирует ГО и лимит маржи `futuresMarginLimitPct`, не учитывает стоп-дистанцию,
а в `OrderManager.evaluateRisk` в `RiskContext` передаётся `BigDecimal.ZERO` как
`currentFuturesMargin` (TODO на месте, `OrderManager.java:201-202`) — RiskGate проверяет маржу
против нуля. `FuturesPositionSizer` не создаётся ни одним бином (ссылки — только тест и javadoc).
Фьючерсный риск-контур этапа 3.2 (ГО-лимит, сайзинг по стопу) существует только на бумаге.

**Рекомендация по исправлению:**

1. Исправить формулу (A7).
2. Зарегистрировать бин `FuturesPositionSizer` в `ApplicationConfig`.
3. В `SignalEngine.submitOrder` для `instrument.isFuture()` вызывать `FuturesPositionSizer.size(...)`:
   - стоп — брать из `signal.getIndicatorSnapshot().get("stop")` (стратегии кладут его туда;
     у `AlligatorAoStrategy` — фрактальный экстремум); при отсутствии стопа — REJECTED с причиной
     `NO_STOP`;
   - `riskCapitalPct` — из `cfg.getParams().get("riskCapitalPct")` (дефолт `"0.01"`);
   - `currentFuturesMargin` — сумма `initialMargin × |контракты|` по фьючерсным позициям из
     `portfolioProvider.positions()` с резолвом спецификации через `InstrumentRepository`;
   - при `marginLimitHit` / 0 контрактов — REJECTED с причиной `MARGIN_LIMIT`.
4. То же значение текущего ГО пробросить в `OrderManager.evaluateRisk` вместо `BigDecimal.ZERO`
   (закрыть TODO на `OrderManager.java:201-202`).
5. Косметика рядом: в `SignalEngine.submitOrder:201-202` в Telegram-payload кладутся заглушки
   `stop = signal.getPrice()`, `stopPct = "0.00"` — заменить на реальный стоп, когда он появится.

## 4. Новые дефекты (stage 3.6–3.7.9) и рекомендации

### 4.1. B1 🔴 Критично: финальные крипто-бары никогда не сохраняются в `bars`

**Файлы:** `src/main/java/com/traderbro/scheduler/CryptoStreamRunner.java:59-68`,
`src/main/java/com/traderbro/storage/BarRepository.java:22-26`

`CryptoStreamRunner.onBar` делает `barStore.upsert(List.of(bar))` **на каждый тик** WebSocket,
включая незакрытые свечи (`is_final=false`). Но `UPSERT_SQL` — `ON CONFLICT (figi, interval, ts)
DO NOTHING`: первый тик новой свечи вставляется, а все последующие — **включая финальный бар с
`x=true`** — отбрасываются конфликтом.

Итог: в `bars` по крипте навсегда остаются OHLCV **первого тика** свечи и `is_final = false`.
Ломается всё, что читает крипто-бары из БД:

- `IndicatorSnapshotService` (Alligator/AO/дивергенции/ангуляции по крипте считаются по
  «первотиковым» свечам);
- `UiController.instruments()` → `latestCloses` → цена крипты на Dashboard — первый тик
  текущей часовой свечи;
- бэктесты по крипте (`BacktestOrchestrator` читает те же `bars`).

Постановка (§3.3) прямо требовала «обновление `bars` с флагом `is_final`» — семантику UPDATE.
T-Bank контур этой ловушки избегает: `StreamManager.onBar` (`StreamManager.java:100-104`)
персистит **только** финальные бары.

**Рекомендация по исправлению (вариант 1, минимальный и консистентный):**

```java
// CryptoStreamRunner.onBar — аналогично StreamManager
private void onBar(Bar bar) {
    try {
        if (bar.isFinal_()) {
            barStore.upsert(List.of(bar));
            snapshotService.onClosedBar(bar);
        }
    } catch (RuntimeException e) {
        log.error("crypto stream: error processing bar {}: {}", bar.getFigi(), e.getMessage());
    }
}
```

**Вариант 2** (если незакрытые свечи в БД действительно нужны для «живой» цены): перевести
`UPSERT_SQL` на `ON CONFLICT (figi, interval, ts) DO UPDATE SET open=EXCLUDED.open,
high=EXCLUDED.high, low=EXCLUDED.low, close=EXCLUDED.close, volume=EXCLUDED.volume,
is_final=EXCLUDED.is_final` — тогда последний тик всегда выигрывает, финализация доезжает.
Вариант 2 меняет семантику для всех поставщиков — принять осознанно (T-Bank контур пишет только
финальные бары, поэтому для него поведение не изменится).

**Обязательно:** Testcontainers-IT — тик `is_final=false` → финальный бар по тому же ts →
в БД финальные OHLCV и `is_final=true`. Плюс разовая чистка уже записанных «первотиковых» свечей
в dev/prod-БД после выката (или полная перезаливка истории крипты — она идемпотентна).

```
[ERROR] The Angular CLI requires a minimum Node.js version of v22.22.3 or v24.15.0 or v26.0.0.
```

**Рекомендация по исправлению:**

```xml
<nodeVersion>v24.15.0</nodeVersion>   <!-- или свежее LTS; npmVersion подобрать под него -->
```

и прогнать `mvn -Pbuild-ui package` end-to-end. Сама Angular-конфигурация верна: ручной прогон
`npm ci && npm run build` под Node v26.13.0 собрал бандл успешно (`Output location: ui/dist/ui`,
`index.html` и чанки в корне, initial 597 kB — в пределах бюджетов `angular.json`). То есть ломает
сборку только устаревший пин Node.

Заодно: `npm ci` сообщает о **38 уязвимостях (2 critical, 1 high)** в lock-файле — прогнать
`npm audit`, обновить уязвимые зависимости UI.

### 4.3. B3 🟡 Ежедневный рефреш крипто-инструментов затирает капитализацию

**Файлы:** `src/main/java/com/traderbro/storage/InstrumentRepository.java:49`,
`src/main/java/com/traderbro/scheduler/CryptoRefreshScheduler.java:29-50`

`UPSERT` по `instruments` перезаписывает `market_cap_usd`/`market_cap_rank` значениями из доменного

капитализация занулена до следующих суток — Dashboard показывает «—».

**Рекомендация по исправлению:** убрать `market_cap_usd`/`market_cap_rank` из SET-части `UPSERT`
(эти колонки ведёт только `updateMarketCap`) либо заменить на
`market_cap_usd=COALESCE(EXCLUDED.market_cap_usd, instruments.market_cap_usd)` (и аналогично rank).

### 4.5. B5 🟡 Мониторинг стримов деградировал после миграции на SDK
