## 1. КОНТЕКСТ И ЦЕЛЬ

Проект называется **TraderBro**. Это **этап 1** более крупной системы (в последующих этапах будут добавлены LLM-контуры — сейчас их НЕ реализуем). Цель этапа — детерминированное, автономное, полностью протестированное ядро:

- получение рыночных данных (исторические свечи + потоковые котировки) **только через T-Bank Invest API** — никаких MOEX ISS, AlgoPack, сторонних источников;
- расчёт индикаторов и генерация сигналов на Ta4j;
- честный бэктест с издержками и walk-forward проверкой;
- жёсткий риск-контур (лимиты, kill-switch, реконсиляция);
- исполнение заявок через T-Bank Invest API в **sandbox-режиме**;
- хранение баров, сигналов, заявок и сделок в PostgreSQL/TimescaleDB;
- REST API мониторинга.

**Архитектурная закладка на будущее:** модули и интерфейсы проектируются так, чтобы позже добавить LLM-уровни без переписывания ядра: стратегии должны принимать внешний `SignalFilter` (сейчас — реализация-заглушка, всегда пропускающая сигналы), а конфигурация стратегий должна читаться из БД и поддерживать горячую перечитку. Никакого кода LLM, клиентов Ollama или внешних API в этом этапе быть не должно.

**Инвариант:** единственный компонент, вызывающий методы выставления заявок, — `OrderManager` в модуле исполнения, и только после прохождения `RiskGate`.

## 4. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 4.1. Клиент T-Bank Invest API (`com.traderbro.data.tbank`)

Реализуй два интерфейса (доменные, в `com.traderbro.core.domain.spi`):

**`MarketDataProvider`** — реализация `TBankMarketDataProvider`:
- `List<Bar> getHistory(String figi, Instant from, Instant to, CandleInterval interval)` — выгрузка исторических свечей через `MarketDataService` SDK с учётом лимитов API на глубину запроса за один вызов (разбивай диапазон на чанки; чанкование вынеси в отдельный тестируемый класс); интервалы: 1 мин, 5 мин, 15 мин, 1 час, 1 день.
- `StreamSubscription subscribeCandles(List<String> figis, CandleInterval interval, Consumer<Bar> onBar)` — подписка на потоковые свечи через `MarketDataStreamService`; обработка переподключения при обрыве стрима (экспоненциальный бэкофф, макс. 5 попыток, затем алерт и флаг деградации).
- `List<Instrument> findInstruments(List<String> tickers)` — поиск FIGI по тикерам через `InstrumentsService` (класс акций, борд TQBR); результат кэшируется в БД (`instruments`), обновление — по расписанию раз в сутки.
- Все вызовы — с таймаутами (конфиг, по умолчанию 10 с); retry **только** для операций чтения (3 попытки, бэкофф); учёт rate-limit ответов SDK (ошибки RESOURCE_EXHAUSTED → пауза + повтор).

**`BrokerGateway`** — реализация `TBankBrokerGateway`:
- `OrderResponse postOrder(OrderRequest)` — выставление лимитной/рыночной заявки через `OrdersService` (тип заявки — из конфига стратегии);
- `void cancelOrder(String orderId)`;
- `List<Position> getPositions()` — через `OperationsService`;
- `List<OrderState> getOpenOrders()`;
- режим `sandbox: true|false` из конфига: sandbox — через `SandboxService` (включая метод пополнения счёта песочницы для тестов); при `sandbox=false` приложение **не стартует**, если в env нет `TRADING_LIVE_ACK=I_UNDERSTAND_RISK`;
- маппинг типов SDK ↔ домен строго в `com.traderbro.data.mapper`; классы SDK не проникают в `core` и `execution`.

**Загрузчик истории** `HistoryLoader` (`CommandLineRunner` за флагом `app.history.load-on-startup`): первичная заливка N лет дневных и M дней минутных свечей по списку инструментов из конфига в гипертаблицу `bars` (уникальный ключ `(figi, interval, ts)`, вставка идемпотентна — `ON CONFLICT DO NOTHING`).

### 4.2. Нормализация данных

- SDK отдаёт цены как `Quotation`/`MoneyValue` (units + nano) — конвертируй в `BigDecimal` в маппере, с юнит-тестами граничных случаев (nano=999999999, отрицательные значения).
- Свечи стрима помечаются «формирующаяся/закрытая»: сигналы стратегий считаются **только по закрытым свечам**; формирующаяся свеча обновляет `bars` с флагом `is_final=false` и перезаписывается при закрытии.
- Часовой пояс хранения — UTC; торговые окна и расписания — `Europe/Moscow`.

### 4.3. Стратегии Ta4j (`com.traderbro.core.strategies`)

Базовая модель ta4j: `BarSeries → Indicator → Rule → Strategy → BaseTradingRecord`. Каждая стратегия реализует интерфейс:

```java
public interface TradingStrategy {
    String id();                                    // уникальный id из strategy_config
    Strategy build(BarSeries series, StrategyParams params);
    Signal evaluate(BarSeries series, StrategyParams params, SignalFilter filter);
}
```

Реализуй:

1. **SmaCrossStrategy** — пересечение SMA(fast)/SMA(slow) (`CrossedUpIndicatorRule` / `CrossedDownIndicatorRule`), лонг-онли, параметры `fast`, `slow` из конфига.
2. **EmaMomentumStrategy** — EMA(12)/EMA(26) + фильтр RSI(14): вход в лонг только если RSI в коридоре `[rsiMin, rsiMax]`; выход по обратному пересечению EMA **или** по стопу ATR(14)·`atrMult` (реализуй стоп как правило выхода через `StopLossRule`-подобную механику ta4j или собственный `Rule`).
3. **BollingerMeanReversionStrategy** — возврат к среднему: вход при касании нижней полосы Боллинджера (20, 2σ), выход при возврате к средней линии; стоп — фиксированный % от цены входа (параметр `stopLossPct`).
4. **DonchianBreakoutStrategy** — пробой верхней границы канала Дончиана N баров, выход — пробой нижней границы M баров.

Общие требования к каждой стратегии:
- принимает `SignalFilter` (интерфейс `double weight(String figi, Direction dir)`; реализация этапа 1 — `NoOpSignalFilter`, всегда 1.0; задел под уровень 2 будущих этапов);
- собственный максимальный размер позиции (% портфеля, параметр);
- каждый сигнал пишется в таблицу `signals`: стратегия, инструмент, направление, цена, снапшот значений индикаторов (JSONB), verdict `ACCEPTED / FILTERED / REJECTED` + причина;
- сайзинг позиции — отдельный компонент `PositionSizer` (по умолчанию: фиксированный % портфеля на сигнал, округление до лотности инструмента).

`StrategyRegistry`: набор активных стратегий и их параметры читается из таблицы `strategy_config` (JSONB-параметры), перечитывается по расписанию (по умолчанию каждые 5 мин) без перезапуска; невалидные параметры → стратегия отключается, событие в аудит.

### 4.4. Бэктест (`com.traderbro.core.backtest`)

- `BacktestRunner`: прогон стратегии по барам из БД с `LinearTransactionCostModel` (комиссия из конфига, по умолчанию 0.05%) и моделью проскальзывания (б.п., по умолчанию 5 б.п.); лонг-онли.
- Метрики (`BacktestMetrics`): CAGR, Шарп, Сортино, Калмар, макс. просадка, win-rate, profit factor, число сделок, средняя длительность позиции, итоговая vs buy&hold.
- **Walk-forward**: скользящие окна train/test (длины из конфига), подбор параметров на train по целевой метрике (конфиг, по умолчанию Шарп), честная оценка на test; сводный отчёт по окнам.
- Результат `BacktestReport` → таблица `backtest_runs` (параметры, метрики JSONB, дата, версия кода/git-hash) + экспорт в Markdown с таблицей метрик в `reports/backtests/`.
- Явный запрет look-ahead: решения только по закрытым барам; обязательный тест `noLookAheadTest` (сдвиг будущих данных не должен менять прошлые сигналы).

### 4.5. Риск-менеджмент и исполнение (`com.traderbro.execution`)

- `RiskGate` — цепочка проверок перед **каждой** заявкой (каждая проверка — отдельный бин `RiskRule` с приоритетом):
  1. kill-switch не активен;
  2. дневной убыток < лимита (по умолчанию 2% портфеля);
  3. позиция по инструменту после сделки ≤ лимита (по умолчанию 10% портфеля);
  4. суммарная экспозиция ≤ лимита (по умолчанию 50%);
  5. частота заявок ≤ N в минуту (по умолчанию 10);
  6. текущее время в торговом окне (конфиг; по умолчанию основная сессия MOEX 10:00–18:40 МСК, торговля в режим выходного дня — отдельный флаг, по умолчанию выключена);
  7. инструмент торгуется (данные стрима живы, lag < T секунд).
     Любой отказ → событие в аудит с причиной, сигнал получает verdict `REJECTED`.
- `OrderManager`: статусная машина `NEW → SENT → PARTIALLY_FILLED → FILLED / CANCELLED / REJECTED / EXPIRED`; клиентский `orderId` (UUID) генерируется и сохраняется в БД **до** отправки (дедупликация, защита от дублей при рестарте); обработка частичных исполнений через подписку на стрим сделок (`OrdersStreamService`); таймаут жизни заявки (конфиг) → отмена; **автоматический retry выставления запрещён** — вместо него сверка статуса по `getOpenOrders()`.
- `Reconciler`: каждые 60 с сверяет внутренние позиции с `BrokerGateway.getPositions()`; расхождение → алерт + (флаг в конфиге, по умолчанию вкл.) автоматический kill-switch.
- `KillSwitch`: отменяет все активные заявки, запрещает новые; опционально (флаг) закрывает позиции рыночными заявками. Активация: вручную через REST, автоматически — по лимиту дневного убытка, по расхождению реконсиляции, по потере стрима данных > T секунд (по умолчанию 60 с). Деактивация — только вручную через REST с подтверждением.
- `StateRecovery`: при старте — восстановление открытых позиций/заявок из БД + сверка с брокером; при несоответствии приложение стартует в режиме «только наблюдение» (сигналы считаются, заявки не выставляются) до ручного подтверждения.

### 4.7. REST API мониторинга (`com.traderbro.app`)

- `GET /api/status` — состояние компонентов (data-stream, broker, db: OK/DEGRADED/DOWN), kill-switch, открытые позиции, P&L дня, lag стрима.
- `GET /api/signals?from=...&to=...` — сигналы с verdict и причинами.
- `GET /api/orders?date=...` — заявки и сделки.
- `GET /api/backtests/{id}` — отчёт бэктеста.
- `POST /api/killswitch/activate` / `POST /api/killswitch/deactivate` — тело `{"confirm": true}` обязательно.
- Аутентификация: API-key в заголовке `X-Api-Key` (значение из env). Управления параметрами торговли через REST нет — только чтение и kill-switch.

### 4.8. Схема БД и миграции (Liquibase, `com.traderbro.storage`)

- Master-changelog `db/changelog/db.changelog-master.yaml` с `includeAll` по каталогам или явными `include`; changeset'ы в YAML, `id` по конвенции `YYYYMMDD-N`, `author` — имя разработчика.
- Таблицы (минимум): `instruments`, `bars` (гипертаблица TimescaleDB — создание гипертаблицы оформи отдельным changeset с `runInTransaction=false`), `signals`, `orders`, `trades`, `strategy_config`, `backtest_runs`, `portfolio_snapshots`, `audit_events`.
- Все денежные поля — `NUMERIC(19,4)`; временные метки — `TIMESTAMPTZ`; JSONB — для снапшотов индикаторов и метрик.
- Откат: для каждого changeset'а, где это осмысленно, укажи `rollback`.

## 5. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

1. **Отказоустойчивость**: обрыв стрима котировок → переподключение с бэкоффом; > 60 с без данных → kill-switch; недоступность БД → остановка торгового контура (нельзя торговать без журнала); ошибки API брокера — классификация (сетевые/лимиты/бизнес-ошибки) с разной реакцией.
2. **Воспроизводимость**: каждый сигнал, решение риск-гейта и заявка — запись в БД с полным контекстом; бэктест по тем же данным обязан давать те же метрики.
3. **Производительность**: расчёт индикаторов по одному инструменту < 50 мс; оконные `BarSeries` (макс. баров в памяти — из конфига, по умолчанию 500); параллельная обработка инструментов через `ExecutorService` с ограничением потоков (конфиг).
4. **Безопасность**: токен T-Bank API — только из env (`TBANK_TOKEN`), никогда в коде/логах; маскирование секретов в логах; версии зависимостей зафиксированы; OWASP dependency-check в профиле CI.
5. **Деньги**: все денежные расчёты торгового контура — `BigDecimal` (scale из конфига, по умолчанию 4); `double` допустим только в метриках отчётности.
6. **Lombok — правила использования**:
  - Разрешено: `@Getter`, `@RequiredArgsConstructor`, `@Slf4j`, `@Builder` (для доменных объектов и DTO), `@Value` (для иммутабельных value-объектов), `@With` (для копирования с изменением).
  - Запрещено: `@Data` (слишком широкий контракт), `@Setter` на сущностях JPA (мутабельность только через методы домена), `@EqualsAndHashCode` без явного `of`/`include` (риск по ленивым коллекциям), `@ToString` без `exclude` для чувствительных полей (токены, суммы).
  - Логирование — только через `@Slf4j` (не `System.out`, не ручной `LoggerFactory`).
  - Конфигурация: `lombok.config` в корне с `lombok.addLombokGeneratedAnnotation = true` (чтобы JaCoCo/SpotBugs корректно обрабатывали сгенерированный код).
7. **Качество кода**: JavaDoc для публичных API пакетов; Checkstyle + SpotBugs; никаких `System.out` — только логгер.

## 6. ТЕСТЫ (обязательны)

- **Юнит-тесты**: каждая стратегия (вход/выход/отсутствие сигнала на синтетических `BarSeries`); `RiskGate` (каждое правило отдельно, включая граничные значения); `OrderManager` (все переходы статусов, дедупликация по UUID, частичный fill, таймаут); `PositionSizer` (лотность, округление); маппер `Quotation → BigDecimal` (граничные случаи); чанкование исторических запросов.
- **Интеграционные (Testcontainers)**: запись/чтение баров, идемпотентность вставки (`ON CONFLICT`), `StateRecovery` после «падения» (записали состояние → перезапуск → восстановили), перечитка `strategy_config`; прогон Liquibase-миграций на чистом контейнере (миграции применяются без ошибок).
- **Контрактный тест** `TBankMarketDataProvider` / `TBankBrokerGateway` — через mock gRPC-сервер или записанные фикстуры ответов SDK (без реального токена и сети).
- **Сквозной тест**: синтетическая история в БД → `BacktestRunner` → отчёт с заранее зафиксированными контрольными метриками.
- **Тест инварианта**: архитектурный тест (ArchUnit) — `core` не зависит от классов SDK брокера; `data` не импортирует `execution`.

## 10. ОГРАНИЧЕНИЯ

- **Никаких LLM**: ни клиентов, ни зависимостей LangChain4j/Ollama, ни промптов — только интерфейс `SignalFilter` и `NoOpSignalFilter` как задел.
- **Единственный источник данных и торговли — T-Bank Invest API**; никаких MOEX ISS, AlgoPack, QUIK, Lua, Python.
- Только JVM-стек; только ta4j для теханализа (никаких проприетарных библиотек).
- Миграции — **только Liquibase** (не Flyway); формат changelog — YAML.
- Слово `robot` не используется нигде: ни в пакетах, ни в модулях, ни в именах классов и артефактов. Проект — **TraderBro**, корневой пакет `com.traderbro`.

- Не выдумывай несуществующие методы SDK/библиотек: если не уверен в точном API ta4j 0.24.x или T-Bank Invest Java SDK — пометь `// TODO: verify API` и предложи альтернативную реализацию.
- Все секреты — только из переменных окружения.
